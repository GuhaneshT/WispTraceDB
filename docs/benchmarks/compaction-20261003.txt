# Comparison with the 26-09-2026 baseline (no compaction)
# ----------------------------------------------------------------------
#
#   RangeQuery       (baseline)  : 2,518,068 ns   743,389 B   13,228 allocs
#   RangeQuery       (compacted) : 12,586,269 ns 3,043,562 B    70,170 allocs
#     -> 5.0x SLOWER, 4.1x more bytes, 5.3x more allocs
#
#   GetSpan          (baseline)  :   140,070 ns    14,547 B       35 allocs
#   GetSpan          (compacted) :   295,814 ns    65,684 B       36 allocs
#     -> 2.1x SLOWER, 4.5x more bytes, same allocs
#
# Reading:
#   - GetSpan B/op rose 4.5x with allocs flat. segment.OpenReader decodes the
#     bloom section on every point lookup (cmd/cmd.go:978 -> reader.go:22);
#     merged segments carry ~30 KB bloom sections vs ~6 KB for a 1000-span
#     segment. The bytes track bloom size, not record size. Direct evidence for
#     Phase 1: the point path must not decode blooms it never consults.
#   - RangeQuery got 5x slower and 5x more allocs. A 1000-ts window sits inside
#     one 5000-span merged segment, so ScanAll decodes all 5000 records and the
#     per-candidate staleness check issues an index.GetSpan for every one of
#     them BEFORE the cheap in-memory time filter (cmd/cmd.go:1186-1203) runs.
#     ~70,170 allocs / 5000 scanned ~= 14 allocs per scanned record.
#     Two follow-ups fall out of this, both correctness-neutral:
#       (1) run filter.matches BEFORE the staleness index lookup, so only the
#           ~101 matching records cost a Pebble point read instead of 5000;
#       (2) iterator-based ScanAll to stop materialising every record.
#     The staleness check itself must stay (deleted spans exist only in the
#     index); only its ordering changes.
